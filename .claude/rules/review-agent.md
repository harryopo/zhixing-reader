# 代码审查 Agent 规范

> **作用**：定义本项目代码审查 Agent 的提示词模板、审查维度、反馈规范和批判性分析框架
> **适用范围**：所有 PR / MR / 功能实现的 AI 辅助审查
> **更新规则**：每季度回顾一次，或在重大架构变更后更新

---

## 一、审查 Agent 提示词模板

### 1.1 标准生产级模板

```
Role: Google Staff Engineer Level 的系统架构师 / 资深代码审查专家
Task: 请按生产级代码审查标准审查下面的代码

Constraints:
- 直言指出安全、性能、可读性、错误处理、可扩展性问题
- 按 Design for Failure 和 Scalability 原则判断
- 不只给建议，必须给可运行的重构版本
- 标出风险等级：P0/P1/P2/P3

Format:
- 先列问题，再给原因，再给修改代码
- 用 Markdown 输出
- 涉及架构流转时使用 Mermaid

Input: 粘贴代码
```

### 1.2 关键设计原理

| 要素 | 作用 | 实践要点 |
|------|------|----------|
| **Role 锚点** | 为模型设定专业基准 | 使用“Google Staff Engineer”“安全审计工程师”等高密度标签，让模型自动切换到线上事故、稳定性、边界条件等审查模式 |
| **硬性约束** | 防止输出“正确的废话” | 拒绝“我希望代码更好”，改为“拒绝只给理论建议，必须给 Production-Ready 重构代码” |
| **三维强制要求** | 确保反馈可落地 | 每项反馈必须包含：**问题定位**（哪段代码危险）+ **风险解释**（业务后果）+ **修改方案**（完整可运行代码，禁止伪代码） |
| **自审指令** | 降低低级错误率 | 追加 `Critique yourself: 写完后，请从安全、性能、边界条件三个角度审查你自己的代码，并修复问题` |

### 1.3 场景化变体

- **安全审查**：按 OWASP Top 10 逐项检查，输出 `[文件:行号] [严重级别] [问题描述] [修复建议]`
- **Bug 检测**：聚焦空指针、边界条件、异步竞态、逻辑分支覆盖
- **架构评审**：要求先分析依赖图，再评估模块边界、循环依赖、数据流一致性
- **多 Agent 编排**：将规范、性能、安全三个维度拆分为独立 Worker 并行执行，最后汇总去重（适用于大型 MR）

## 二、标准审查类目 / 维度

### 2.1 基础质量层（每轮必查）

| 维度 | 审查重点 | 典型问题 |
|------|----------|----------|
| **正确性** | 边界条件、空值处理、循环终止、状态一致性 | 未检查 null 就访问属性、除零错误、循环越界 |
| **可读性** | 命名描述性、注释质量、控制流清晰度 | 使用 `temp`/`data` 等无意义命名、过度嵌套三元表达式、过度“聪明”的技巧代码 |
| **可维护性** | 模块化程度、耦合度、内聚性、重复代码比例 | 超长函数（>50 行）、God Class（>500 行）、深层嵌套（>4 层） |
| **测试覆盖** | 单元测试、边界用例、测试质量 | 核心状态机无自动化测试、测试仅追求覆盖率数字 |

### 2.2 设计架构层（人工 + AI 协同）

| 维度 | 审查重点 | 评估标准 |
|------|----------|----------|
| **架构一致性** | 是否遵循 SOLID、DDD 边界划分 | 职责单一、接口稳定、无循环依赖 |
| **设计模式** | 是否合理使用模式，而非为了模式而模式 | 仅在存在耦合问题时使用模式，需说明解决的具体问题 |
| **数据流设计** | 数据流向是否清晰、是否有跨层直接访问 | 上层不得依赖下层实现细节 |
| **接口设计** | RESTful 规范、版本控制、幂等性 | 接口一旦发布禁止破坏性修改，支持向后兼容 |

### 2.3 安全合规层（高风险阻断项）

| 维度 | 审查重点 |
|------|----------|
| **注入漏洞** | SQL 注入、NoSQL 注入、命令注入、SSRF |
| **敏感信息泄露** | 硬编码密钥、注释中的密码、日志中的敏感数据 |
| **权限控制** | 认证绕过、批量赋值（mass assignment）、CORS 配置过宽 |
| **依赖安全** | 已知漏洞（CVSS ≥ 7）、abandoned packages、许可证合规 |

### 2.4 性能与运维层

| 维度 | 审查重点 |
|------|----------|
| **算法效率** | N+1 查询、无界循环、O(N²) 复杂度 |
| **资源管理** | 连接池释放、内存泄漏、未关闭的 I/O |
| **异步与并发** | 竞态条件、事务边界、线程安全 |
| **可观测性** | 日志完整性、指标埋点、链路追踪、告警覆盖 |

### 2.5 技术债务层（持续监控）

| 债务类型 | 识别信号 |
|----------|----------|
| **架构债** | 循环依赖、服务拆分不合理、单点故障 |
| **代码债** | 重复逻辑、超长方法、缺少边界校验 |
| **数据债** | 字段语义混乱、无唯一约束、历史脏数据 |
| **测试债** | 核心状态机无自动化测试 |
| **运维债** | 无监控、无告警、无回滚、配置靠人工修改 |
| **安全债** | 依赖漏洞、权限过宽、密钥散落 |
| **文档债** | 接口契约缺失、恢复手册和负责人缺失 |

**排序模型**：`优先级 ≈ 业务影响 × 发生概率 × 变更频率 × 修复耗时`

## 三、批判性分析框架

### 3.1 分层审查框架

```
第一层：静态规则层（机器完成）
  ├── 代码格式（ESLint / Prettier / Checkstyle）
  ├── 圈复杂度阈值
  ├── 重复代码率
  └── 依赖漏洞扫描

第二层：语义分析层（AI Agent 完成）
  ├── 逻辑正确性
  ├── 边界条件与异常路径
  ├── 安全反模式（SQL 注入、XSS、硬编码密钥）
  └── 性能反模式（N+1、无界循环）

第三层：架构决策层（人工主导）
  ├── 业务语义正确性
  ├── 权限边界与灰度策略
  ├── 历史债务权衡
  └── 技术选型与演进路径
```

**核心原则**：AI 放在人工审查前面做初审，拦截低级问题；人集中精力看设计取舍和业务风险。

### 3.2 多维度并行审查（三维审查法）

| 维度 | 负责模型/工具 | 独有优势 |
|------|---------------|----------|
| **规范一致性** | Claude（长上下文） | 发现跨文件的不规范问题 |
| **性能分析** | Gemini（全库索引） | 追踪完整数据流，发现隐藏性能隐患 |
| **安全审查** | GPT-5.5 / DeepSeek-R1 | 缺陷模式识别，边界条件穷举 |

**执行方式**：三个维度并行触发，各自独立扫描后汇总去重，按严重程度分三级：
- **阻塞项**：未修复禁止合入
- **建议项**：记录在案供人工判断
- **优化项**：不阻塞但提示改进方向

### 3.3 架构评审关键检查点

| 检查类别 | 关键问题 |
|----------|----------|
| **架构风格** | 架构风格是否明确？是否采用合适的架构模式（MVC、分层、微服务、事件驱动）？ |
| **模块划分** | 模块职责是否单一（SRP）？模块间耦合度是否低、内聚性是否高？ |
| **接口设计** | 接口职责是否单一？是否支持版本化和向后兼容？ |
| **技术选型** | 技术栈是否成熟可控？是否与团队技能匹配？社区活跃度和长期支持情况？ |
| **非功能需求** | 性能、安全性、可伸缩性、可观测性在架构层面是否有映射？ |
| **演进能力** | 核心域是否稳定？非核心域是否可快速演进且隔离？ |
| **故障隔离** | 是否考虑了失败场景和回滚机制？是否有降级、熔断、限流策略？ |

### 3.4 SubAgent 分布式审查架构

对于大型变更（>1000 行），推荐采用 **SubAgent 任务分片机制**：

- **任务分解**：将复杂审查任务拆分为可并行执行的子任务
- **专业分工**：针对特定技术栈动态调配专精子代理（如 React 优化专家、SQL 安全审计师）
- **上下文同步**：通过分布式上下文总线实现跨代理信息共享
- **安全隔离**：每个子代理运行在独立容器中，通过文件系统访问控制防护

## 四、建设性反馈表达方式

### 4.1 反馈表达的三段式结构

```
1. 问题定位：指出哪段代码危险（精确到文件:行号）
2. 风险解释：把"可能有问题"翻译成业务后果
3. 修改方案：给出完整代码，不要伪代码
```

**反面教材**：
> “建议增强错误处理。”（怎么增强？在哪里增强？会不会改变接口行为？）

**正面示范**：
> “这里没有重试机制，支付回调抖动时会造成状态不一致。建议增加指数退避重试，最多 3 次，并在第 3 次失败时写入死信队列通知人工介入。”

### 4.2 Conventional Comments 规范

使用标准化前缀标签，让反馈类型一目了然：

| 标签 | 含义 | 示例 |
|------|------|------|
| `suggestion:` | 提出改进或替代方案 | `suggestion: Consider using a loop here for better scalability.` |
| `issue:` | 指出 Bug、安全漏洞或功能问题 | `issue: This function does not handle null inputs properly.` |
| `question:` | 寻求澄清或更多上下文 | `question: Why did you choose this algorithm over another?` |
| `nitpick:` | 轻微的风格或格式问题 | `nitpick: Consider using single quotes for consistency.` |
| `praise:` | 认可优秀代码或决策 | `praise: Great job optimizing this function!` |
| `thought:` | 提出一般性想法，不一定需要行动 | `thought: Would it be beneficial to modularize this function?` |
| `todo:` | 记录稍后处理的事项 | `todo: Refactor this function to reduce complexity.` |

### 4.3 反馈语气原则

| 原则 | 说明 | 示例对比 |
|------|------|----------|
| **对事不对人** | 关注代码行为，不评判开发者 | ❌ “你怎么能这样写？” → ✅ “这里用策略模式替代 if-else 链会更易扩展，是否考虑重构？” |
| **具体而非模糊** | 避免“这段代码写得很差” | ❌ “这个函数太复杂” → ✅ “这个函数有 8 层嵌套，建议拆分为 `validateInput`、`processData`、`formatOutput` 三个子函数” |
| **提供替代方案** | 不说“fix this”，而是给出方案 | ✅ “Have you considered caching this?” beats “This is wrong.” |
| **先肯定再建议** | 建立心理安全 | ✅ “这个缓存机制实现得很清晰！如果加上 LRU 淘汰策略，内存占用会更可控。” |
| **区分阻塞与建议** | 明确优先级 | “必须修改（阻塞性问题）” vs “建议修改（优化建议）” |

### 4.4 结构化输出模板

对于 AI Agent，输出结构应标准化为表格或编号列表，便于直接贴入 PR 评论区：

| 文件:行号 | 问题类型 | 严重程度 | 具体原因说明 | 推荐修改方案 |
|----------|----------|----------|--------------|--------------|
| `OrderService.java:156` | 性能 | 🔴 阻塞项 | 循环内调用 `CouponService.restore()`，批量取消 10 个订单产生 10 次 DB 查询 | 改为 `CouponService.batchRestore()` 一次批量处理 |
| `OrderService.java:89` | 安全 | 🔴 阻塞项 | 库存释放和状态更新不在同一事务内，释放成功后状态更新失败会导致数据不一致 | 使用 `@Transactional` 包裹整个取消方法 |
| `OrderService.java:203` | 风格 | ⚠️ 建议项 | `TimeoutCancelEvent` 未继承项目 `EventBase` 基类 | 统一继承以获得 `traceId` 和 `timestamp` 字段 |

### 4.5 严重程度定义

| 级别 | 标识 | 定义 | 处理方式 |
|------|------|------|----------|
| **阻塞项** | 🔴 | 会导致生产事故、数据丢失、安全漏洞 | 必须修复，否则禁止合入 |
| **建议项** | ⚠️ | 影响代码质量、可维护性、扩展性 | 记录在案，由 maintainer 判断是否修复 |
| **优化项** | 💡 | 不影响功能，但可以更好 | 可选修复，作为技术债务记录 |
| ** nitpick** | 💬 | 风格/格式问题 | 可选修复，不影响合入 |

## 五、本项目特定审查要点

### 5.1 Electron 特有审查点

| 审查点 | 检查内容 |
|--------|----------|
| **IPC 安全** | preload.ts 是否只暴露必要 API，是否有 `contextBridge` 绕过 |
| **safeStorage** | 敏感数据是否走系统级加密，是否有硬编码密钥 |
| **主进程阻塞** | 是否有同步 IPC 调用导致渲染进程卡顿 |
| **内存泄漏** | 事件监听器是否正确移除，流式读取是否正确释放 |

### 5.2 本项目架构约束

| 约束 | 审查要点 |
|------|----------|
| **单文件行数** | `database.ts` / `ipc.ts` / `ai-service.ts` 允许超过 500 行，但必须有拆分计划 |
| **Repository 层** | 业务代码应通过 Repository 访问 DB，禁止直接引用裸 DB 对象 |
| **IPC 通道** | 必须走 `shared/ipc-channels.ts` 常量，禁止裸字符串 |
| **类型安全** | 禁止 `as any`，`Record<string, unknown>` 需要特殊审批 |
| **测试覆盖** | 新增代码覆盖率 ≥ 85%，核心路径必须有集成测试 |

### 5.3 技术债务优先级

根据项目现状，以下债务需要优先关注：

| 债务 | 严重度 | 识别信号 |
|------|--------|----------|
| `database.ts` 单文件 2000+ 行 | P1 | 计划拆但未动 |
| `ipc.ts` 单文件 800+ 行 | P1 | 同上 |
| Repository 层虚假分层 | P1 | 有接口但业务代码绕过 |
| `weread-api.ts` 模块级可变状态 | P1 | `let apiKey` + `const cache` 模块级变量 |
| `Record<string, unknown>` 滥用 | P2 | 30+ 文件使用 |
| `Stats.tsx` 2700+ 行 | P2 | Phase 7 标注待拆 |
| `AgentOrchestration.tsx` 1900+ 行 | P2 | 同上 |

## 六、审查流程

### 6.1 标准审查流程

```
1. AI Agent 初审（本规范）
   ├── 静态规则检查（ESLint / TypeScript）
   ├── 语义分析（逻辑、边界、安全、性能）
   └── 输出结构化报告

2. 人工架构审查
   ├── 业务语义正确性
   ├── 权限边界与灰度策略
   ├── 历史债务权衡
   └── 技术选型与演进路径

3. 修改与复核
   ├── 开发者修改阻塞项
   ├── Agent 复核修改
   └── 人工确认建议项处理方式

4. 合入
   └── 三绿门禁（lint + typecheck + test + build）
```

### 6.2 大型变更（>1000 行）审查流程

```
1. 任务分片
   ├── 规范维度 Worker
   ├── 性能维度 Worker
   └── 安全维度 Worker

2. 并行审查
   └── 三个维度独立扫描

3. 汇总去重
   ├── 合并重复问题
   ├── 按严重度排序
   └── 生成结构化报告

4. 人工复核
   └── 架构决策层审查
```

### 6.3 审查输出模板

```markdown

## 问题汇总
```

### 7.2 术语表

|------|------|

| **竞态条件** | 多线程/异步环境下，程序行为依赖于事件执行的相对时间 |
| **IPC** | Inter-Process Communication，进程间通信 |
